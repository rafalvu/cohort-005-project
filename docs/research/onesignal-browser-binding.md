# OneSignal browser subscription binding

Researched 2026-11-17 for [Validate secure OneSignal browser subscription binding](https://github.com/rafalvu/cohort-005-project/issues/9). Documentation/source review only; no account, credentials, live notifications, vendor contact, or application changes.

## Decision

**Insufficient evidence to approve OneSignal for secure account-bound browser push.** Direct subscription targeting is documented, but the reviewed material does not establish that a browser subscription remains bound to the same delivery endpoint after an application verifies possession. A generic verification push is a proposed application protocol, not a documented OneSignal authentication feature. Its initial proof cannot establish future endpoint integrity.

There is a documented blocker to the straightforward alternative: OneSignal currently says Web SDK identity verification is unsupported, warns that enabling its app-wide toggle prevents web registration, and says knowledge of an External ID permits impersonation without verification. An opaque External ID is therefore not authentication. [Identity verification](https://documentation.onesignal.com/docs/en/identity-verification)

This leaves the production-provider decision open. It does not disprove every possible integration. Keep the agreed application-owned Notifications/read state in SQLite/Drizzle, QStash triggers plus recovery scans, separate Postmark refund emails, $50/month incremental ceiling, and event-relative 24-hour push expiry. Trusted application authentication is a prerequisite; the development user selector cannot supply it. These are ticket constraints, not vendor guarantees.

## What primary sources establish

| Boundary | Evidence | Consequence |
| --- | --- | --- |
| Sending | The server API accepts `include_subscription_ids`, up to 20,000 IDs, independently of alias targeting; these targeting modes cannot be combined. | A server-owned user → verified subscription map can avoid External ID routing. The targeting option itself supplies no ownership proof. [Push API](https://documentation.onesignal.com/reference/push-notification) |
| Secrets | App ID is public; App API key is private and authorizes message creation. | Keep sending credentials server-side. This does **not** imply every SDK subscription operation requires that key. [Keys & IDs](https://documentation.onesignal.com/docs/en/keys-and-ids) |
| Subscription identity | Subscription ID is immutable; subscription properties can be updated asynchronously. | Immutable ID does not mean immutable endpoint or owner. [Update subscription](https://documentation.onesignal.com/reference/update-subscription) |
| Ownership | A subscription can move between OneSignal users within one app; SDK `login` is the recommended path. | Distinguish changing its OneSignal owner from changing the browser to which it delivers. Direct-ID targeting avoids alias fan-out but does not prove either invariant. [Transfer subscription](https://documentation.onesignal.com/reference/transfer-subscription) |
| Browser identity | Web `logout()` unlinks the External ID and creates an anonymous OneSignal user. | That is not evidence that an application’s stored direct-ID binding has been revoked. [Web SDK](https://documentation.onesignal.com/docs/en/web-sdk-reference#logout) |

### Public SDK mutation is the decisive unknown

Inspected official SDK `main` at immutable commit [`02f64c2c80faf61b926881734cd545d3bd83d4d5`](https://github.com/OneSignal/OneSignal-Website-SDK/commit/02f64c2c80faf61b926881734cd545d3bd83d4d5), whose commit timestamp is 2026-11-17. This is a source snapshot, not a verified deployed CDN version.

- [`api.ts`](https://github.com/OneSignal/OneSignal-Website-SDK/blob/02f64c2c80faf61b926881734cd545d3bd83d4d5/src/core/requests/api.ts#L184-L245) updates `/apps/{appId}/subscriptions/{subscriptionId}` without request authentication options. Its comment explicitly says this route accepts an unsigned request and rejects a bearer. Creation and owner-transfer use the common optional-JWT request path.
- [`SubscriptionOperationExecutor.ts`](https://github.com/OneSignal/OneSignal-Website-SDK/blob/02f64c2c80faf61b926881734cd545d3bd83d4d5/src/core/executors/SubscriptionOperationExecutor.ts#L194-L210) includes `token`, `web_auth`, and `web_p256` in that update, alongside enabled/status fields. [`base.ts`](https://github.com/OneSignal/OneSignal-Website-SDK/blob/02f64c2c80faf61b926881734cd545d3bd83d4d5/src/shared/api/base.ts#L96-L122) adds Origin/SDK/content headers, with Authorization only when a JWT option exists.
- There is documentation/source drift: this snapshot exposes [`login(externalId, jwtToken?)`](https://github.com/OneSignal/OneSignal-Website-SDK/blob/02f64c2c80faf61b926881734cd545d3bd83d4d5/src/onesignal/OneSignal.ts#L100-L118) and [identity-verification gates](https://github.com/OneSignal/OneSignal-Website-SDK/blob/02f64c2c80faf61b926881734cd545d3bd83d4d5/src/core/identityVerification.ts), while the support documentation still excludes Web. The documentation also lists subscription updates among JWT-gated APIs, in tension with the unsigned-route comment. Neither observation proves the supported production behavior.

**Inference, not an exploit finding:** if a caller knowing a victim’s subscription ID can replace its endpoint and encryption fields with another browser’s valid values, a verified binding could later deliver to that browser. SDK code proves the client request shape, not what OneSignal’s server accepts. Server validation, token deduplication, or endpoint-ownership checks could reject that substitution. Their guarantees are absent from the inspected sources. Browser same-origin restrictions and a public Origin header are not proof of account authorization, particularly for a non-browser caller. A negative sandbox result also needs an explanation of the enforced invariant before treating it as a security contract.

## Verification-push proposal and its limits

The following is a protocol hypothesis to test, not implementation approval:

1. A CSRF-protected, authenticated application request starts a pending binding for `(user, session, subscription ID, binding generation)`. Rate-limit attempts. Generate a high-entropy single-use secret, store its hash with a short expiry (for example five minutes), and deliver the secret **only through a generic push** to that exact subscription. Do not return it in the initiating response or include personal notification content.
2. Opening the notification may display a confirmation page; GET/HEAD, link previews, prefetch, and SDK click/receipt callbacks must not activate the binding. Require an explicit same-origin POST, CSRF validation, the still-valid initiating user/session, the matching pending tuple, and atomic unused → consumed transition. Reject altered IDs, replay, expiry, logout, and concurrent account switches. Keep challenge URLs out of analytics/referrers/logs; do not treat a challenge URL as a login credential.
3. The intended evidence is that someone possessing this session also obtained a secret delivered to this subscription at this time. A submitted UUID, local SDK getter, or receipt alone supplies no such proof. Relay, stolen-session, and same-origin script compromise remain outside the guarantee; a copyable secret is not device attestation.
4. Activation remains unsafe unless subsequent subscription endpoint changes are authenticated or invalidate the binding before any send. Periodic checks or repeating a challenge reduce exposure but leave a check/send race. No reviewed documented verification design establishes this continuing integrity property.

### Platforms, session context, and logout

Desktop and Android browsers support the Web SDK on documented compatible browsers, with HTTPS, service worker, permission, and origin requirements. They do not inherit native Android SDK identity-verification support. [Web push FAQ](https://documentation.onesignal.com/docs/en/web-push-setup-faq)

iOS/iPadOS 16.4+ requires opening an installed Home Screen web app and requesting permission through user interaction; an ordinary browser tab cannot subscribe. [OneSignal iOS setup](https://documentation.onesignal.com/docs/en/web-push-for-ios) Apple documents cookie copying when installing a Home Screen app starting in 17.2, followed by separate website data; other local storage is not copied. Thus installation, multiple app copies, login location, and notification-click context matter. [WebKit 17.2](https://webkit.org/blog/14787/webkit-features-in-safari-17-2/), [WebKit Home Screen apps](https://webkit.org/blog/13878/web-push-for-web-apps-on-ios-and-ipados/)

**Protocol consequence:** authenticate and start enrollment inside the intended app context. If its notification click has no matching session, fail closed and restart enrollment after authentication; do not silently bind to whichever account opens the link. The reviewed sources do not guarantee session continuity for every click/cold-start path. Test it on real iPhone/iPad devices.

Revoke the application binding and pending challenges on logout/account switch, increment its generation, and recheck authorization at dispatch. SDK logout alone is insufficient for direct-ID routing. Revocation cannot promise to retract a push already handed to a transport or displayed: OneSignal distinguishes canceling unsent notifications from removing delivered ones. [Push cancellation](https://documentation.onesignal.com/docs/en/push#cancel-push-notifications) Therefore generic content plus an authenticated destination limits shared-device disclosure; account-specific lock-screen content requires an explicit decision about that residual race. A server-side read before sending is not atomic with provider delivery.

## Idempotency, expiry, and receipts

- Persist one UUID idempotency key per logical notification send and reuse it after ambiguous failures. OneSignal retains notification keys for 30 days and returns the original result for duplicates; reusing a key for a different operation suppresses that operation. This is request deduplication, not a promise of exactly-once display. [Idempotency](https://documentation.onesignal.com/reference/idempotent-notification-requests)
- `ttl` is offline validity in seconds, defaults to three days, and accepts 0–28 days. Cadence must calculate the remaining interval to `event time + 24 hours`, skip expired work, and preserve the deadline across recovery/retries; setting 86,400 seconds at every delayed send would extend it. Avoid provider scheduling/delivery optimization that extends the window. Server/provider queue timing and already displayed notifications need separate validation; TTL is not an authenticated read-state or retraction mechanism. [Push API](https://documentation.onesignal.com/reference/push-notification)
- A successful HTTP response must be checked for a nonempty notification ID and recipient errors. [Push API](https://documentation.onesignal.com/reference/push-notification) Delivered means transport acceptance; Confirmed Receipt means SDK receipt, requires a paid plan, and is unsupported for Safari web push. It does not establish the logged-in account, user reading, or challenge redemption. Keep read state in Cadence. [Confirmed receipt](https://documentation.onesignal.com/docs/en/confirmed-delivery)

## Minimal discriminating next gate — not performed

Prerequisites: separately authorize a disposable vendor sandbox and generic live test sends, provide trusted test authentication, two controlled accounts/browser profiles, and physical iPhone/iPad access. Record SDK/CDN version, app configuration, request/response traces, resulting IDs/endpoints, and actual recipient. No purchase or vendor contact is authorized by this report.

1. **Establish the supported security contract.** Reconcile the Web documentation with the pinned source and deployed version. Obtain documented/vendor confirmation of which creation, identity, owner-transfer, update-by-ID/token, delete, and legacy subscription routes accept public callers; what proof protects endpoint changes; and what happens on token deduplication. Check toggle-off and any explicitly supported toggle-on configuration.
2. **Attempt cross-browser mutation in the sandbox.** Enroll A, retain A’s verified ID, and from B try owner reassignment and replacement with B’s endpoint/keys using only public SDK-visible data. Repeat with same-origin browser and non-browser requests, duplicate creation, token rotation, deletion/recreation, and supported legacy routes. Send a generic probe to A’s original ID after each operation. Pass requires an explained invariant preventing unauthorized redirection, or fail-closed invalidation before sending; accepting an unauthorized redirect rejects this design. Alias reassignment alone must not be mislabeled endpoint hijacking.
3. **Exercise enrollment abuse and platform context.** Submit A’s ID from B; spoof user/session/subscription fields; replay, expire, prefetch, and cross-site-submit challenges; race two activations and logout. None may activate the wrong binding. Run desktop Chrome/Firefox/Safari, Android Chrome, and iOS/iPadOS Home Screen warm/cold clicks, expired sessions, and separate installations. Missing/wrong session must fail closed.
4. **Exercise dispatch races and deadlines.** Queue a generic send, go offline, logout/switch accounts, reconnect, and inspect delivery/click authorization. Retry an ambiguous send with its stored idempotency key; recover work near/after the event’s 24-hour deadline. Distinguish transport acceptance, device receipt, display, and authenticated read. Record unavoidable already-in-flight delivery rather than claiming logout cancels it.

Research completion closes the evidence-gathering question only. Production approval requires a human review of the missing integrity guarantee and these results; no sandbox test is represented as passed.
